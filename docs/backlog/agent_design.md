# 에이전트 설계 (LangGraph, 챗봇형)

2026-10-19. 사용자와 질문·답을 주고받으며 정한 설계다. **"결정"으로 표시한 것은 사용자가 고른 것**이고, "제안"은 결정에서 따라 나오는 구체안(Claude), "확인 필요"는 구현 전에 공식 문서로 확인해야 하는 가정이다. 아직 구현하지 않았다. 2026-10-19에 구현 전 확인과 스파이크를 했고 결과는 7·7-1·7-2에 있다.

## 2. 구조 (제안)

```
사용자 메시지
   │
   ▼
[agent 노드] LLM이 대화 기록과 상태를 보고 다음 행동을 고른다
   │  ├─ 도구 호출 ─▶ [tools 노드] 검증·한도 확인 후 실행, 결과를 상태에 기록 ─┐
   │  ├─ ask_user(missing=[...]) ─▶ 코드 템플릿으로 되묻기 문구를 만들어 응답   │
   │  ├─ decline(reason=...) ─▶ 고정 안내 문구로 응답                          │
   │  └─ 끝(finish)                                                             │
   │◀─────────────────────────────────────────────────────────────────────────┘
   ▼
[render 노드] 코드가 결과 표를 만들고(숫자·접수번호·정정 여부·이어받은 조건),
              LLM의 설명 문장은 숫자 검사를 통과할 때만 덧붙인다
   ▼
응답 = 완료된 요청의 표 + (있으면) 모아서 한 번에 묻는 되묻기
```

- **도구(`tools.py`):** `resolve_years`, `resolve_company`, `get_financials`, `compute_ratio`. 모두 예외 없이 `status`가 담긴 결과를 돌려준다.
- **의사 도구 2개(구현은 코드):** `ask_user(missing)`는 빠진 항목(회사·연도·작업·후보 선택 등)을 구조화해서 넘기면 코드가 문구를 만든다. `decline(reason)`은 이유 코드(`OFF_TOPIC`, `INVESTMENT_ADVICE`, `PRICE_FORECAST`, `UNSUPPORTED_METRIC`, `UNSUPPORTED_PERIOD` 등)를 넘기면 코드가 고정 문구를 만든다. LLM은 이 둘로만 되묻고 거절하므로 문구가 매번 같다.
- **연도:** LLM은 날짜를 계산하지 않고 표현(`explicit`/`range`/`relative`/`recent`)만 `resolve_years`에 넘긴다.
- **복수 요청:** 회사×연도 조합을 요청 하나로 보고 요청마다 상태(`done`/`pending`/`unsupported`/`error`)를 둔다. 일부가 실패해도 나머지는 보여 준다.

## 3. 상태 (제안)

| 필드 | 내용 |
|---|---|
| `messages` | 대화 기록(모델에는 최근 몇 턴만 전달, 길이는 구현 때 정함) |
| `context` | 직전에 확정된 회사·연도·작업·기준(후속 질문 이어받기용, 이어받으면 화면에 표시) |
| `requests` | 요청 목록과 요청별 상태·결과·오류 코드 |
| `resolved` | 이 대화에서 `resolve_company`가 확정해 준 회사(`corp_code`) 목록 |
| `counters` | 이번 질문의 요청 수, 도구 호출 수 |
| `tool_log` | 호출한 도구·인자·결과 상태·소요 시간(평가와 화면의 실행 기록에 사용, LangSmith와 별개) |

## 4. 안전 규칙 (제안)
1. **한도:** 요청 10개, 도구 호출 40회를 넘으면 임의로 자르지 않고 "줄여 달라"고 안내한다.
2. **중복 호출 방지:** 같은 도구·같은 인자는 이전 결과를 재사용한다(성장률의 전기 조회와 겹치는 호출 포함).
3. **인자 검증은 도구가 한다:** 연도 범위, 기준(연결·별도), 기간(연간만), 회사 코드는 반드시 `resolve_company`가 이 대화에서 확정해 준 것만 허용한다(LLM이 코드를 지어내지 못하게).
4. **설명 문장에는 숫자를 쓰지 못한다:** 숫자(연도 포함)가 하나라도 있으면 그 문장을 버리고 표만 보여 준다(LLM이 숫자 형식을 바꾸는 것이 스파이크에서 확인되어 "도구 결과에 있는지" 검사 대신 이 규칙으로 바꿨다).
4-1. **근거 인용 검증(결정 14):** `resolve_years`·`resolve_company`는 `evidence`가 대화의 사용자 문장에 있어야 하고, `basis=별도`는 사용자가 "별도"를 말했을 때만, 분기·월 `period`는 사용자가 그렇게 말했을 때만 허용한다. `get_financials`·`compute_ratio`의 `corp_code`는 이 대화에서 확정된 것만, `year`는 `resolve_years`가 준 것만 허용한다.
5. **투자 판단·예측 금지:** 이 범위의 요청은 `decline`으로만 처리하고, 설명 문장에도 전망·추천을 쓰지 않도록 시스템 지시에 명시한다.
6. **프롬프트 주입:** 도구 결과와 사용자 입력은 데이터로 취급한다. 숫자는 코드가 만들기 때문에 LLM이 지어낼 경로가 없다.
7. **오류 시 안전하게 멈춤:** LLM 호출 실패·형식 오류는 사용자에게 알리고 임의 값으로 대체하지 않는다. 호출 한도·시간 제한은 코드로 강제한다.

## 5. 화면 (제안)
- Streamlit 채팅. 완료된 결과 표 + 되묻기를 한 응답에 함께 보여 준다.
- 후보 버튼과 텍스트 답변(예: "첫 번째", "NAVER")을 모두 받는다. 텍스트는 직전 후보 목록 안에서만 확정한다.
- 이어받은 조건과 해석한 이름(입력→해석), 접수번호·접수일·정정 여부를 표시한다.
- 실행 기록 패널에 `tool_log`(도구 호출 기록)를 보여 준다.

## 6. 평가 (결정 13 + 제안)
- **정답:** 도구 호출 집합(이름과 정규화한 인자, 순서 무시)과 최종 표(요청별 상태·숫자). 같은 질문 3회 반복.
- **새 질문 묶음:** 복수 연도, 복수 회사, 회사×연도, 후속 질문, 상대 연도(날짜 고정), 별도·분기·월, 정정본, 동명 회사, 유명 별칭·후보 확인, 지원 밖·딴소리. 기존 `final`, `real`은 사용하지 않는다.
- **지표:** 호출 집합 일치, 최종 표 일치, 불필요한 호출 수, 도구 호출 수, 지연, 토큰, 위험 오답(조용히 틀린 값) 수.
- **기준선 비교:** 단일 요청 질문에서 `baseline-single-request`와 같은 질문·같은 반복 횟수로 비교한다.
- LangSmith 월 한도가 소진되어 있어도 평가가 되도록, 평가는 `tool_log`를 사용한다.

## 7-1. 스파이크 결과 (단일 실행, 시나리오별 한 번이라 일반화할 수 없다)
시스템 지시와 도구 6개(`resolve_years`, `resolve_company`, `get_financials`, `compute_ratio`, `ask_user`, `decline`)로 시험했다. 한 턴에 2~6초, 도구 호출 2~7회.

| 시나리오 | 기대 | 실제 | 판정 |
|---|---|---|---|
| 삼전이랑 닉스 2024년 영업이익률 | 두 회사 확정 후 계산 | 두 회사를 유명 별칭으로 바로 확정하고 계산 | 맞음 |
| 삼성전자 영업이익률 (연도 없음) | **연도를 되묻기** | 연도를 묻지 않고 "올해"로 추측해 오류를 받자 "작년"으로 바꿔 2025를 계산 | **틀림(조용한 추측)** |
| → "2024" (이어서) | 이전 조건 이어받기 | 삼성전자·영업이익률을 이어받아 2024 계산 | 맞음 |
| 삼성전자 2024년 1분기 영업이익 | 지원 안 함 안내 | 조회 없이 `decline(UNSUPPORTED_PERIOD)` | 맞음 |
| 삼성전자 올해 영업이익률 | 올해는 공시 전이라고 안내하고 되묻기 | 직전 연도(2025)로 **마음대로 바꿔 계산**, 도구에 영어 코드(`CFS`, `annual`)를 넣어 오류 3번 후 성공(7회 호출) | **틀림(조용한 대체, 낭비)** |
| 애플 2024년 영업이익 | 해외 기업 안내 | `resolve_company`가 조회 불가를 돌려줬는데 `decline(OFF_TOPIC)`로 거절 이유를 잘못 고름 | 이유 코드가 틀림 |
| SK하이닉스 2024 매출 성장률 | 바로 계산 | 도구에 연결/별도 값을 잘못 넘겨 오류가 나자 사용자에게 "연결인가요 별도인가요?"를 불필요하게 되물음 | 불필요한 되묻기 |

## 7-2. 스파이크로 얻은 설계 수정안 (2026-10-19 사용자 승인, 결정 14~18로 확정)
1. **조용한 추측 방지: 근거 인용 검증.** 연도·회사처럼 사용자가 말한 값을 쓰는 도구 인자에 `evidence`(사용자 문장에서 그대로 인용한 부분)를 필수로 받고, 코드가 그 문구가 실제 대화에 있는지 검사한다. 사용자가 말하지 않은 "올해"나 "작년"을 LLM이 지어서 쓰면 도구가 거부하고 `ask_user`로 되돌린다. 시스템 지시만으로는 막지 못했다(위 시나리오 2번, 5번).
2. **인자는 열거형으로 고정.** `basis`는 `연결|별도`, `period`는 `연간`만, `metric`은 정해진 값만 받도록 도구 스키마의 `Literal`로 제한한다(영어 코드 `CFS`·`annual` 시도와 불필요한 되묻기 제거).
3. **도구가 안 된다고 한 이유는 코드가 그대로 보여 준다.** `status`가 `unsupported`/`error`로 오면 도구의 사용자용 메시지를 응답에 쓴다. `decline`은 연간 재무와 무관한 요청과 투자 판단·예측에만 쓰게 하고, 도구가 이미 준 이유를 LLM이 다른 코드로 바꿔 말하지 못하게 한다.
4. **큰 결과를 LLM이 다시 넘기지 않게 한다.** `compute_ratio`가 조회 결과 전체를 받는 대신 `corp_code`, `year`, `basis`를 받아 내부에서 같은 조회 결과를 재사용한다(스파이크에서 이렇게 바꿔야 도구 호출이 안정적이었다). `tools.compute_ratio`는 에이전트용 얇은 래퍼를 추가한다.
5. **숫자 검사 규칙 변경.** LLM이 숫자를 다시 쓸 때 형식을 바꿨다(도구가 준 300,870,903,000,000원을 "약 300조 8,709억 원"으로). 그래서 "문장의 숫자가 도구 결과에 있는지" 검사는 형식이 달라 통과시키기 어렵다. **설명 문장에는 숫자를 쓰지 못하게(숫자가 있으면 문장 폐기) 하고, 숫자는 코드가 만든 표로만 보여 준다.**
6. **응답 내용이 블록 목록으로 온다.** `langchain-google-genai`의 응답 `content`가 텍스트 조각과 서명 정보가 섞인 목록이라, 텍스트만 뽑아 쓰는 코드가 필요하다.
7. **호출 낭비 억제.** 위 1·2번이 적용되면 줄어들 것으로 보이며, 구현 후 평가에서 호출 수를 측정한다.

## 8. 아직 정하지 않은 것
- 되묻기·거절 템플릿의 구체적인 문구
- 모델에 전달하는 대화 기록 길이(턴 수), 응답 시간 제한
- 후속 질문에서 이어받을 수 있는 범위(회사만? 연도만? 작업까지?)의 세부 규칙. 스파이크에서는 회사·연도·작업을 모두 이어받았고 잘 동작했지만 어디까지 허용할지는 정하지 않았다
- 설명 문장의 길이와 어조


## 10. 구현 현황 (2026-10-19)
구현 파일: `agent_core.py`(상태·도구 실행·검증·답변 조립), `chat_app.py`(챗봇 화면), `tests/test_agent.py`·`tests/fakes.py`(가짜 LLM 테스트 59개), `eval/run_agent_eval.py`와 평가셋 두 개. 결과는 [eval_results.md](../evaluation/eval_results.md) 8차.

설계(결정 1~18)를 구현했고 평가에서 확인해 **설계보다 강화·추가한 것**:
| 항목 | 내용 |
|---|---|
| 근거 인용 | 사용자 문장의 일부이기만 한 인용은 우회되었다. 연도 인용은 해당 연도 숫자·상대 연도 단어·"최근"이 들어 있어야 하고, 회사 인용은 이름과 같은 말이어야 한다(후보 목록 중 하나를 "1번"처럼 고르는 경우만 예외) |
| 지표 검사 | 사용자가 실적·영업이익률·성장률 등을 말하지 않으면 지표를 정해서 조회하지 못한다(어휘 목록, 불필요한 되묻기가 생길 수 있는 쪽으로 틀리게 설계) |
| 후보 처리 | 후보 없이 `ask_user(candidate)`를 못 하게 막고, 후보가 나왔는데 되묻지 않고 끝나면 코드가 되묻기를 붙인다 |
| 누락 고지 | 확정된 회사인데 표도 안내도 없으면 "조회 결과를 만들지 못했다"고 알린다 |
| 도구가 이유를 줬을 때 | 일반 거절 문구(`OFF_TOPIC`)는 도구의 안내가 있으면 붙이지 않는다 |
| 헛돎 방지 | 검증 오류가 4번 쌓이면 중단하고 되묻는다. 그래프 재귀 한도 예외는 사용자 안내로 바꾼다 |
| 일시 오류 | NETWORK/API 오류는 캐시하지 않는다 |
| 사용량 기록 | 턴마다 토큰·LLM 호출 수를 `usage`에 기록 |

**아직 안 한 것·알려진 한계**
- (2026-10-19 어려운 질문 Q&A, eval_results.md 9차에서 발견) 직전 답변의 연도를 기준으로 한 상대 표현("그 전년도는?")은 되묻는다. 설명 문장이 하지 않을 계산("몇 배인지 계산해 드립니다")을 약속할 수 있다. 분기+연간을 함께 물으면 전체를 거절한다(연간만 답하고 분기만 안내하는 편이 나음).
- 후속 질문 이어받기 실패는 원인(인용 문구의 "년" 접미사 불일치 등)을 찾아 고쳤고 임시 시험 96/96이었다(eval_results.md 8-5). 새 질문 묶음으로는 재측정하지 않았다.
- 화면은 AppTest로 동작만 확인했고 브라우저에서 직접 눌러 보는 확인은 하지 않았다.
- 대화 기록 길이(최근 12턴 전달)와 이어받기 범위의 세부 규칙은 임의로 정했고 평가하지 않았다.
- LangSmith 추적은 월 한도가 소진되어 쓰지 않았고, 평가는 `tool_log`로 했다.
- 후속 질문·복수 요청의 평가는 짧은 시나리오 위주다. 긴 대화는 평가하지 않았다.
