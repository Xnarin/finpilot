# 앞으로 고려할 요구사항과 예외 상황 (golden set 후보)

작성일 2026-10-17. **아직 구현하지 않았고 평가하지도 않은 항목**이다. 현재 시스템은 질문 하나가 `(기업 1곳, 연도 1개, 작업 1개)`로 정해진다는 가정 위에 있다. 아래 요구가 들어오면 이 가정이 깨지므로, 에이전트를 만들기 전에 구조를 먼저 정한다.

## 1. 지금의 가정과 깨지는 지점

| 현재 가정 | 깨지는 요구 | 지금 동작 |
|---|---|---|
| 질문 1개 = 요청 1개 `{기업, 연도, 작업}` | "삼성전자 2023~2025년 영업이익률", "삼성전자·SK하이닉스 2024년 비교" | 복수 회사는 company를 비우고 중단, 복수 연도는 가장 최근 연도 하나만 해석(비교 질문일 때) |
| 연도는 정수 하나 | 범위("최근 3년"), 목록("2022, 2024"), 상대 표현("작년") | 연도가 없으면 중단, 상대 표현은 null |
| 한 번의 조회가 곧 답 | 결과 일부만 성공(한 회사는 조회되고 다른 회사는 실패) | 단일 요청이라 부분 성공 개념이 없음 |
| 작업은 세 가지 중 하나 | "영업이익률이랑 성장률 같이", "누가 더 높아?" | task를 비우고 중단 |
| 숫자는 화면 하나로 표시 | 회사×연도 표, 비교, 추이 | 단일 결과 카드 |

## 2. 에이전트 구조에 대한 메모 (결정 필요)

1. **해석과 실행을 분리한다.** LLM은 질문을 요청 목록 `requests: [{company, year, task}, ...]`로만 바꾸고, 실행은 코드가 목록을 순회한다. 숫자는 계속 OpenDART 조회와 코드 계산으로만 만든다.
2. **요청마다 상태를 둔다.** 각 요청이 성공·실패·되묻기 필요를 따로 갖고, 일부 실패해도 나머지 결과는 보여 준다(부분 성공). 전체를 한 번에 실패시키지 않는다.
3. **되묻기는 요청 단위로 한다.** 회사명이 모호한 요청만 후보를 묻고, 확정된 요청은 먼저 실행한다.
4. **상한을 둔다.** 한 질문당 최대 요청 수(예: 회사×연도 합 20개), OpenDART 일일 호출 한도, 요청 간 대기. 상한을 넘으면 줄여 달라고 안내하고 임의로 잘라 실행하지 않는다.
5. **캐시.** 같은 (회사, 연도, 기준) 조회는 한 질문 안에서 한 번만 호출한다. 성장률의 전기 조회가 다른 요청의 당기 조회와 겹친다.
6. **비교의 정의를 먼저 정한다.** 회사 간 비교는 같은 사업연도·연결 기준·원 단위일 때만 허용한다. 결산월이 다르거나 기준이 섞이면 비교 불가 이유를 표시한다.
7. **작업 확장은 별도로.** 복수 작업 요청은 "요청 목록의 각 항목이 자기 작업을 가진다"로 풀 수 있다. 우열·순위·추이 같은 새 작업은 정의(공식, 동률, 결측 처리)부터 쓴 뒤 추가한다.
8. **평가 단위가 바뀐다.** 정답이 단일 필드 일치에서 "요청 목록 전체의 집합 일치"로 바뀐다. 순서 무시, 중복 제거, 누락·초과 요청을 구분해서 채점한다.

## 4. golden set 파일 형식 제안

현재 `eval/questions.json`은 단일 요청 정답이다. 복수 요청으로 가면 아래처럼 확장한다.

```json
{
  "id": "M01", "split": "dev_multi", "category": "multi_company_multi_year",
  "question": "삼성전자, SK하이닉스 2023~2025 영업이익률",
  "expected_requests": [
    {"company": "삼성전자", "year": 2023, "task": "영업이익률 계산"}
  ],
  "expected_outcome": "OK | ASK | STOP | PARTIAL",
  "expected_error_codes": [],
  "notes": "정책 결정이 필요한 항목은 pending_policy 로 표시"
}
```

- `category`로 묶어서 약한 영역을 바로 볼 수 있게 한다(연도·회사·조합·데이터·표현).
- 정책이 정해지지 않은 항목(Y03, Y05, Y10, D03 등)은 `pending_policy`로 두고 점수에 넣지 않는다.
- 해석 평가(LLM)와 실행 평가(코드)를 분리한다. 실행은 고정 요청 목록과 가짜 OpenDART 응답으로 API 비용 없이 반복 실행한다.
- dev/final 분리 원칙은 유지한다. final은 프롬프트·코드를 고칠 때 보지 않고, 한 번 본 final은 새 묶음으로 교체한다.

## 5. 정책 결정이 필요한 항목

1. "최근 N년"과 "올해/작년"의 기준 연도(오늘 날짜 vs 가장 최근 공시 연도)
2. 한 질문당 최대 요청 수와 OpenDART 호출 한도 대응
3. 정정공시·재작성 수치 선택 기준
4. 거꾸로 쓴 연도 범위, 중복 요청의 처리
5. 비교 작업(우열·순위·변화폭)의 정의와 `%`/`%p` 표기
6. 금융업 지원 여부
7. 복수 요청 질문에서 일부 해석이 불확실할 때 먼저 실행할지, 전부 되물을지
